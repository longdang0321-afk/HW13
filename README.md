과제 13: 병합 정렬과 퀵 정렬의 성능 비교
0. 요약
- Merge Sort와 세 가지 피벗 방식의 Quick Sort를 같은 원본 데이터로 실행하고, 여섯 크기에서 비교 횟수·실행시간·추가 메모리를 비교하였다.
- Merge Sort는 모든 크기에서 값 비교 횟수가 가장 적었지만, 실행시간이 가장 짧지는 않았다.
- 실행시간은 First가 세 크기, Median-of-Three가 세 크기에서 가장 짧아, 모든 크기에서 가장 빠른 단일 방법은 없었다.
- n=20,000에서 Merge는 260,949회, 2.330000 ms, 80,744 Byte였다. Median-of-Three는 333,185회, 2.197500 ms, 1,176 Byte로 세 Quick Sort 중 세 항목 모두 가장 작았다.
- 메모리는 실제 RAM 실측값이 아니라 임시 배열과 재귀 깊이, 변수 크기를 이용한 추정값이다.

각 크기에서 데이터 seed를 다시 초기화한다. 정렬 직전 피벗 seed도 초기화하여 같은 크기와 방법의 반복에서 같은 피벗 순서를 사용한다. 400회는 같은 입력을 반복한 것이며 서로 다른 400개 입력의 평균은 아니다.
2.2 정렬 방법
방법	동작	피벗 선택의 값 비교
Merge Sort	두 구간을 각각 정렬한 뒤 임시 배열로 병합	해당 없음
Quick First	현재 구간의 첫 원소 선택	없음
Quick Random	현재 구간에서 무작위 위치 선택	없음
Quick Median-of-Three	처음·가운데·마지막 값의 중앙값 선택	분할마다 3회


Quick Sort는 선택한 피벗을 마지막으로 옮긴 뒤 같은 Lomuto 분할을 사용한다. 피벗보다 작은 값은 왼쪽, 크거나 같은 값은 오른쪽으로 보낸다. Merge Sort는 n개의 int 임시 배열을 한 번 할당하여 모든 재귀 호출에서 공유한다.
2.3 비교 횟수 집계
구분	포함 항목	제외 항목
Merge	병합 중 a[i] <= a[j]	남은 원소 복사, 인덱스/종료 조건, 검증
Quick	분할 중 a[j] < pivot, Median3 선택의 값 비교	난수 생성, 교환, 인덱스/종료 조건, 검증


2.4 실행시간 측정
매 반복에서 배열 복사와 seed 초기화를 끝낸 뒤 정렬 호출 직전에 시작하고, 반환 직후 종료한다. 시간을 ms로 변환한 후 400회 평균을 구한다.
포함	제외
정렬, Merge 임시 배열 할당·해제, 비교/깊이 계측과 메모리 추정 계산	데이터 생성, 배열 복사, seed 초기화, 결과 검증, 출력


따라서 출력 시간은 계측 코드를 포함한 CPU 시간이다. 비교 횟수와 메모리는 400회 누적이 아니라 한 번의 정렬 값이다.
2.5 메모리 계산 방법
추가 메모리는 다음 변수 크기 모델로 계산하였다.
재귀 공간 = 최대 활성 재귀 깊이 × 재귀 함수 1회의 변수 크기

Merge = n × sizeof(int) + 재귀 공간 + 진입/보조 함수 공간
Quick = 재귀 공간 + 진입/보조 함수 공간
- depth의 최댓값으로 최대 재귀 깊이를 기록한다. 종료된 호출까지 모두 누적하지 않는다.
- 함수별 공간은 매개변수와 지역 변수의 타입 크기를 sizeof로 합산한다.
- Quick의 보조 공간은 partition → choose_pivot → swap 경로의 변수 공간을 더한다. Merge는 병합 함수 공간을 더한다.
- 공통 원본/작업 배열과 실험용 통계 구조체 저장 공간은 제외한다.
- 반환 주소, 저장 레지스터, 패딩, 컴파일러 임시 공간, 할당기 관리 정보와 표준 라이브러리 내부 공간은 계산하지 않는다.
최대 재귀 깊이와 보조 함수의 최대 공간이 동시에 발생하지 않을 수 있으므로, 이 값은 계산 모델의 추정값이며 실제 최대 스택이나 프로세스 RAM의 정밀 측정값은 아니다.

4. 비교·분석
4.1 데이터 크기 증가에 따른 비교 횟수 변화
크기 변화	Merge	First	Random	Median3
1,000 → 2,000	2.23배	2.06배	2.30배	2.31배
2,000 → 4,000	2.21배	2.33배	2.14배	2.08배
4,000 → 8,000	2.19배	2.23배	2.39배	2.15배
8,000 → 16,000	2.17배	2.16배	2.04배	2.28배


Merge는 데이터가 두 배가 될 때 약 2.17~2.23배, 세 Quick Sort는 약 2.04~2.39배 증가하였다. 이는 이번 입력에서 O(n log n)에 가까운 증가 경향과 부합한다. 유한한 입력의 결과만으로 모든 입력에 대한 복잡도를 증명하는 것은 아니다.

Merge는 구간을 균등하게 나누어 O(log n)단계를 만들고 각 단계에서 O(n)의 병합을 수행한다. Quick은 피벗에 따라 남는 구간의 크기가 달라지므로 증가 배율도 더 흔들린다. 이번 데이터에서는 Merge가 여섯 크기 모두 가장 적게 비교하였다.

16,000 → 20,000은 데이터가 두 배가 아니라 1.25배가 되는 구간이다. 이 구간을 위의 두 배 증가 구간과 같은 기준으로 비교하지 않았다.
4.2 두 알고리즘의 실행시간 차이
크기	가장 짧게 측정된 방법
1,000 / 8,000 / 20,000	Quick Median-of-Three
2,000 / 4,000 / 16,000	Quick First


Merge는 값 비교가 가장 적었지만, 임시 배열에 저장한 뒤 원본 배열로 다시 복사하고 메모리를 할당·해제한다. Quick은 배열 안에서 교환하며 분할한다. 따라서 비교 횟수만으로 실행시간을 설명할 수 없다. 함수 호출, 데이터 이동, 계측 등도 시간을 사용한다.

예를 들어 n=2,000에서 Merge는 19,426회로 First의 23,410회보다 적게 비교했지만 시간은 0.202500 ms로 First의 0.160000 ms보다 길었다. 반면 n=1,000에서는 Merge가 First보다 조금 짧았다. 이번 결과를 모든 입력에서 Quick이 더 빠르다는 뜻으로 해석하지 않는다.

n=20,000에서 Merge 2.330000 ms와 First 2.325000 ms는 매우 비슷하다. 이런 작은 차이는 타이머 해상도와 실행 환경의 변동을 고려해야 하며, 차이의 원인을 별도 측정 없이 확정하지 않는다.
4.3 두 알고리즘의 메모리 사용량 차이
Merge의 추정 메모리는 n=1,000에서 4,544 Byte, n=20,000에서 80,744 Byte였다. sizeof(int)=4인 환경에서 20,000개의 임시 배열만 80,000 Byte이므로, 추가 공간은 O(n) 배열이 지배한다.

Quick의 n=20,000 추정값은 1,176~1,500 Byte로 훨씬 작았다. 별도의 n개짜리 배열은 없지만 재귀 호출이 있으므로 O(1) 공간이라고 할 수 없다. 평균적으로 O(log n), 최악에는 O(n)의 호출 공간을 사용한다.

메모리는 데이터 크기보다 최대 활성 호출 깊이에 직접 영향을 받는다. First의 추정값이 8,000개에서 1,320 Byte, 16,000개에서 1,284 Byte로 줄어든 것도 이 계산 방식 때문이다. Median3는 여섯 크기 모두 세 Quick Sort 중 가장 작은 메모리 추정값을 보였다.
4.4 피벗 선택 방법에 따른 성능 차이
판단 기준	결과
Quick 중 비교 횟수 최소	Random 3회, Median3 2회, First 1회
Quick 중 실행시간 최소	First 3회, Median3 3회
Quick 중 메모리 추정값 최소	Median3 6회
n=20,000의 Quick 세 지표	Median3가 모두 최소


n=20,000에서 Median3는 333,185회로 First보다 약 8.27%, Random보다 약 7.79% 적게 비교하였다. 선택 비용을 포함하고도 전체 비교량이 감소한 결과이다. 그러나 n=2,000에서는 25,720회로 세 방법 중 가장 많이 비교하였다.

현재 구간 길이가 m이면 Lomuto 분할 자체는 피벗과 무관하게 m−1번 비교한다. 피벗은 그다음 남는 두 구간의 크기를 바꾼다. 중앙값에 가까우면 균형 잡힌 분할을 기대할 수 있고, 극단값이면 한쪽에 원소가 많이 남는다.

First는 선택 비교가 없고, Random은 입력의 특정 위치에 고정되지 않지만 난수 생성 비용이 있다. Median3는 세 값의 가운데를 고르지만 전체 중앙값을 보장하지 않으며 분할마다 3번 비교한다. 분할 개선과 선택 비용이 함께 작용하므로 한 방법이 항상 가장 좋지는 않다. 특히 n=16,000에서는 Random이 First보다 적게 비교했지만 실행시간은 더 길었다.
5. 시간 복잡도 및 공간 복잡도
알고리즘	최선 시간	평균/기대 시간	최악 시간	추가 공간
Merge Sort	O(n log n)	O(n log n)	O(n log n)	O(n) 배열 + O(log n) 스택
Quick First	O(n log n)	무작위 입력에서 보통 O(n log n)	O(n²)	평균 O(log n), 최악 O(n)
Quick Random	O(n log n)	서로 다른 값에서 피벗 난수에 대한 기대 O(n log n)	O(n²)	보통 O(log n), 최악 O(n)
Quick Median3	O(n log n)	무작위 입력에서 보통 O(n log n)	O(n²)	평균 O(log n), 최악 O(n)


Merge는 분할 크기가 균등하여 최악에도 O(n log n)이지만 임시 배열이 필요하다. Quick은 균형 잡힌 분할에서 O(n log n)으로 동작하지만 한쪽으로 계속 치우치면 비교가 (n−1)+(n−2)+…+1에 가까워져 O(n²)이 된다. 현재 구현은 양쪽을 그대로 재귀 호출하므로 그 경우 스택도 O(n)이 된다.

또한 < pivot인 Lomuto에서는 모든 값이 같으면 세 피벗 방법 모두 한쪽으로 치우친다. Random이나 Median3도 이 중복 입력에서의 최악 동작을 제거하지 않는다.
6. 결론
1. 이번 입력에서 Merge는 모든 크기에서 가장 적게 비교하였고, 네 방법의 비교 횟수는 대체로 O(n log n)에 가까운 증가 경향을 보였다.
2. 비교가 적다고 시간이 항상 짧지는 않았다. Merge의 병합/복사와 메모리 할당, Quick의 교환 및 피벗 선택 등의 비용도 영향을 준다.
3. 실행시간은 First와 Median3가 각각 세 크기에서 가장 짧았다. n=20,000에서는 Median3가 2.197500 ms로 가장 짧았다.
4. Merge는 O(n)의 임시 배열 때문에 메모리가 더 컸고, Quick은 주로 재귀 깊이에 따른 공간을 사용하였다. 메모리 출력은 2.5절의 계산 기준에 따른 추정값이다.
5. n=20,000에서는 Median3가 세 Quick Sort 중 가장 좋은 세 지표를 보였지만, 피벗 방식의 성능은 입력과 선택 비용에 따라 달라지므로 항상 우수하다고 결론 내리지는 않는다.
