## 2. 측정 기준

### 2.1 숫자 비교 횟수

Merge Sort는 병합할 때 두 값 `a[i] <= a[j]`를 비교한 횟수를 센다. 한쪽 구간에 남은 원소를 복사하는 작업에는 비교 횟수를 추가하지 않는다.

Quick Sort는 분할 중 `a[j] < pivot` 비교와 Median-of-Three 선택 과정의 세 번 비교를 포함한다. First와 Random의 피벗 선택 자체에는 데이터 값 비교가 없다. 반복문 인덱스, 종료 조건 및 결과 검증의 비교는 제외한다.

### 2.2 실행시간

정렬 호출 직전과 직후에 `clock()`을 호출한다. 차이를 `CLOCKS_PER_SEC`로 나눈 뒤 1,000을 곱하여 ms로 변환하고, 400회 결과의 평균을 출력한다.

| 구분 | 항목 |
|---|---|
| 제외 | 데이터 생성, 배열 복사, seed 초기화, 결과 확인 및 출력 |
| 포함 |정렬 수행, Merge Sort 내부 임시 배열의 할당/해제, 비교 횟수와 재귀 깊이를 기록하는 연산, 메모리 추정 계산 |

따라서 계측된 프로그램의 실행시간이다. `clock()`은 실제 경과시간이 아닌 CPU 시간을 측정한다.

### 2.3 추가 메모리

메모리는 프로파일링 도구의 실측값이 아니라 `sizeof`와 최대 재귀 깊이를 사용하는 변수 크기 모델의 추정값이다.

```text
재귀 공간 = 최대 재귀 깊이 × 재귀 함수 1회의 매개변수/지역 변수 크기

Merge = n × sizeof(int) + 재귀 공간 + 진입/보조 함수 공간
Quick = 재귀 공간 + 진입/보조 함수 공간
```

최대 깊이는 재귀 함수의 depth를 이용하여 기록한다. 호출이 끝난 뒤에도 모든 호출의 공간을 누적하는 방식은 사용하지 않는다. Merge Sort는 n개의 `int` 임시 배열을 한 번 할당하여 모든 재귀 호출이 공유한다. Quick Sort는 별도의 동적 보조 배열을 사용하지 않는다. 진입 함수와 보조 함수 공간도 코드에 정의된 변수 크기의 합으로 계산한다.

| 구분 | 항목 |
|---|---|
| 제외 | 공통 원본/작업 배열, 실험용 통계 구조체의 저장 공간 |
| 계산하지 않음 | 반환 주소, 저장 레지스터, 패딩, 컴파일러의 최적화와 임시 공간, 할당기 관리 정보, 표준 라이브러리 내부 공간 |

또한 최대 깊이와 보조 함수의 최대 공간이 실제로 동시에 발생하지 않을 수 있다. 따라서 출력값을 실제 최대 스택이나 프로세스 RAM과 동일하다고 해석하지 않는다.

## 4. 비교·분석

### 4.1 데이터 크기와 비교 횟수

Merge Sort는 1,000개에서 8,698회, 2,000개에서 19,426회, 4,000개에서 42,847회로 증가하였다. n이 두 배가 되면 비교 횟수는 두 배보다 조금 더 증가하였다. 배열을 균등하게 나누는 단계 수가 O(log n)이고 각 단계의 병합 비용이 O(n)이므로 O(n log n) 동작과 부합한다.

이번 데이터에서는 모든 크기에서 Merge Sort의 비교 횟수가 가장 적었다. Quick Sort는 피벗 위치에 따라 좌우 구간 크기가 달라진다. 한쪽으로 치우친 분할이 많아지면 더 많은 단계에서 비교하게 된다. 따라서 같은 데이터에서도 피벗 방법에 따라 비교 횟수가 달라졌다.

### 4.2 실행시간 차이

2,000 / 4,000 / 16,000개에서는 First가 가장 짧았고, 1,000 / 8,000 / 20,000개에서는 Median3가 가장 짧았다. 한 방법이 모든 크기에서 가장 빠르지는 않았다.

Merge Sort는 비교 횟수가 가장 적었지만 실행시간이 항상 가장 짧지는 않았다. 임시 배열에 병합하고 원래 배열로 다시 복사하는 작업과 메모리 할당/해제가 필요하기 때문이다. Quick Sort는 배열 내부에서 분할하며, Random에는 난수 생성 비용이 있고 Median3에는 추가 피벗 선택 비용이 있다. 함수 호출과 계측 연산도 실행시간에 영향을 준다. 다만 이번 측정만으로 각 비용의 기여도를 따로 확정할 수는 없다.

20,000개에서 Merge와 First의 시간은 각각 2.3300 ms와 2.3250 ms로 거의 같았다. 이러한 작은 차이만으로 확실한 우열을 주장하기는 어렵다. 타이머 해상도와 실행 환경의 변동을 고려해야 한다.

### 4.3 메모리 차이

Merge Sort의 추정 메모리는 1,000개에서 4,544 Byte, 20,000개에서 80,744 Byte였다. n에 비례하는 임시 배열이 대부분을 차지하기 때문에 데이터 증가에 따라 메모리도 크게 증가했다.

Quick Sort의 20,000개 결과는 1,176~1,500 Byte로 Merge보다 작았다. 하지만 재귀 호출이 있으므로 추가 공간을 O(1)이라고 할 수는 없다. 추정 메모리는 최대 재귀 깊이에 영향을 받는다. First의 값이 8,000개에서 1,320 Byte, 16,000개에서 1,284 Byte인 것처럼, 입력 크기가 증가해도 최대 깊이가 더 작으면 메모리가 감소할 수 있다.

### 4.4 피벗 방법에 따른 차이

20,000개에서 Median3는 333,185회로 First의 363,224회와 Random의 361,327회보다 적게 비교했고 실행시간도 가장 짧았다. 이 입력에서는 중앙값 선택 비용을 포함해도 분할 개선의 효과가 나타났다.

그러나 2,000개에서는 Median3가 25,720회로 세 방법 중 가장 많이 비교했다. 세 값의 중앙값이 전체 구간의 정확한 중앙값인 것은 아니며, 선택 비용도 추가된다. Random 역시 특정 난수 수열에서 가장 좋은 결과를 보장하지 않는다. 따라서 이번 한 seed의 결과를 모든 입력에 일반화하지 않는다.

## 5. 복잡도 정리

| 알고리즘 | 최선 시간 | 평균/기대 시간 | 최악 시간 | 추가 공간 |
|---|---|---|---|---|
| Merge Sort | O(n log n) | O(n log n) | O(n log n) | O(n) 배열 + O(log n) 스택 |
| Quick First | O(n log n) | 무작위 입력에서 보통 O(n log n) | O(n²) | 평균 O(log n), 최악 O(n) |
| Quick Random | O(n log n) | 서로 다른 값에서 피벗 난수에 대한 기대 O(n log n) | O(n²) | 보통 O(log n), 최악 O(n) |
| Quick Median3 | O(n log n) | 무작위 입력에서 보통 O(n log n) | O(n²) | 평균 O(log n), 최악 O(n) |

현재 Quick Sort는 양쪽 구간을 그대로 재귀 호출하므로 분할이 계속 치우치면 스택이 O(n)까지 증가할 수 있다. 특히 `< pivot`을 사용하는 Lomuto에서는 모든 값이 같은 경우 세 피벗 방법 모두 O(n²) 시간과 O(n) 재귀 공간을 사용할 수 있다. Random과 Median3도 이 문제를 없애지는 못한다.

Merge Sort는 분할 크기가 균등하여 최악에도 O(n log n)을 유지하지만 O(n)의 임시 배열이 필요하다. 현재 Merge Sort는 같은 값에서 왼쪽 원소를 먼저 선택하므로 안정 정렬이고, 현재 Quick Sort는 안정 정렬이 아니다.
